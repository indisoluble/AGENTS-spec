# Open questions about enduring behavior

Use these questions when deciding what a future contract must preserve. Start with the accepted requirement linked in each entry. Follow an example to read its precise conditions. Its suite cites the Design specification and contract clauses that govern the mechanism in use today. The [acceptance summary](../../02-formulation/deliverables/baseline.md#behavioral-acceptance-and-editorial-provenance) establishes the scope of the requester’s decision. The choices below concern details beyond that scope.

## Which activities count as inquiry?

[BR4](../../02-formulation/deliverables/baseline.md#br4--bounded-investigation-and-timely-reassessment) requires timely notice and bounded investigation when uncertainty remains after relevant context gathering and blocks the next decision. The boundary matters for both proportionate effort and requester awareness.

- [BR4.4](proposed-examples/bounded-inquiry.md#br44--ordinary-checking-does-not-require-an-inquiry-notice) asks about ordinary reading and regression checks without a blocking uncertainty. [BR4.6](proposed-examples/bounded-inquiry.md#br46--a-prescribed-procedure-can-still-be-inquiry) varies the purpose of a documented benchmark. Using it to decide how to proceed and using it to validate a settled limit exercise different conditions.
- [BR4.7](proposed-examples/bounded-inquiry.md#br47--reading-existing-project-documents-remains-context-gathering) isolates the harder case. A question already blocks the next decision, but reading an existing architecture record may answer it. The [inquiry design](../../03-design/deliverables/mechanisms/bounded-inquiry.md#when-inquiry-applies) and [contract §1.1](../../04-candidate/pre_AGENTS.md#11-plan--define-the-next-increment) classify **all** reading of existing project documentation as context gathering, even then.

Which of these detailed exclusions and purpose distinctions must every equivalent contract preserve? In particular, must reading always receive that treatment? The open decision concerns the scope of the trigger. Existing authorization, limits, notification duties, and reassessment still apply.

## How precisely must a source or a limit be classified?

- Under [BR2](../../02-formulation/deliverables/baseline.md#br2--evidence-based-planning-and-knowledge-ownership), the owner of the relevant knowledge matters when an instruction file and project configuration disagree. Must every contract assign those artifacts the precise roles used in [BR2.4](proposed-examples/planning-and-scope.md#br24--use-instruction-files-for-conduct-not-proof-of-project-facts)? The [knowledge ownership design](../../03-design/deliverables/mechanisms/knowledge-and-documentation.md#documentation-choices) and [contract §1.1](../../04-candidate/pre_AGENTS.md#11-plan--define-the-next-increment) explain the current rule. The distinction affects which source settles a project fact.
- Under [BR3](../../02-formulation/deliverables/baseline.md#br3--autonomy-within-authorization-and-prior-direction), the agent must respect requester-imposed limits. [BR3.4](proposed-examples/authorization-and-communication.md#br34--do-not-pass-a-checkpoint-or-enlarge-a-limit-on-your-own) illustrates an explicit cap. [BR3.8](proposed-examples/authorization-and-communication.md#br38--distinguish-an-expectation-from-a-binding-limit) explores an informal expectation of a small fix. Must the exact distinction in [contract §2.3](../../04-candidate/pre_AGENTS.md#23-effort-estimates-and-requester-limits) define when a future contract requires another requester decision?

## Which debt and dead-code details must persist?

- [BR8](../../02-formulation/deliverables/baseline.md#br8--durable-knowledge-without-expanded-editing-authority) establishes durable-finding duties and editing boundaries. [BR8.3](proposed-examples/knowledge-and-documentation.md#br83--optional-debt-recording-does-not-authorize-a-fix) explores when an evidenced compromise may be recorded as debt. [BR8.7](proposed-examples/knowledge-and-documentation.md#br87--update-recorded-debt-when-authorized-work-resolves-it) explores the duty to update an existing entry after authorized work resolves it. Which [classification, optional recording, and conditional maintenance rules](../../03-design/deliverables/mechanisms/knowledge-and-documentation.md#recording-technical-debt) must future contracts preserve? The distinction affects what gets recorded and when. Recording debt grants no repair authority.
- [BR9](../../02-formulation/deliverables/baseline.md#br9--engineering-quality-and-preservation) establishes focused changes and preservation. In [BR9.5](proposed-examples/engineering-quality.md#br95--no-textual-caller-is-not-proof-of-dead-code), a handler has no textual caller but might be registered dynamically. Must the precise [dead-code evidence rule](../../03-design/deliverables/mechanisms/engineering-and-validation.md#engineering-scope-boundaries) govern future removal decisions? Scope and preservation already apply.

## What response must a documentation gap trigger?

[BR10](../../02-formulation/deliverables/baseline.md#br10--affected-requirements-and-documentation) covers affected documentation and out-of-scope gaps. Compare [BR10.3](proposed-examples/knowledge-and-documentation.md#br103--report-gaps-outside-the-authorized-work), which reports an unrelated gap, with [BR10.4](proposed-examples/knowledge-and-documentation.md#br104--a-documentation-gap-does-not-require-a-new-guide), which concerns a known gap within scope and a deferred improvement. Which details of the [documentation design](../../03-design/deliverables/mechanisms/knowledge-and-documentation.md#documentation-choices) must endure concerning proposals, deferral, qualified improvements, and an agreed need for a new guide? The answer affects what a contributor proposes or writes within existing editing authority.

## What can proceed to Formulation?

The requester or an authorized delegate can settle the enduring rule and separately decide whether a particular example defines it. Existing approvals stand. For bridges and references, [PR1 and its qualifications](../../02-formulation/deliverables/baseline.md#established-product-requirement) identify the accepted delivery and authorization boundaries. No separate provider-policy requirement or BR11 was established.

Review of proposed formulations and examples, requirements-derived automation, and any separately authorized redesign remain future work. For a partial or complete decision, follow the [Discovery handoff](../docs/maintaining-discovery.md#pass-a-decision-to-formulation) and the [shared BDD iteration](../../docs/pipeline.md#test-first-iteration).
