# 02.1 — Acceptance

Formulation records what the requester or authorized delegate accepts as a requirement. Acceptance defines how to evaluate it. Start with the accepted rule, applicable constraints and any expressly accepted defining example in [`02.0-formulation/deliverables/baseline.md`](../02.0-formulation/deliverables/baseline.md). Derive the expected outcome from that source, independently of selected mechanisms and Candidate wording. A mechanism change that preserves the requirement should normally leave the criterion applicable.

Acceptance owns requirements-derived scenarios, fixtures, assertions, qualitative criteria, executable evaluation definitions and their coverage. Establish the expectation before mechanism selection. Implement and exercise executable checks as soon as feasible. A written criterion followed by qualified assessment can also evaluate a requirement. Record which method was used, the conditions and observations it needs, and the limits of what it can establish. Available methods include behavioral trials, artifact inspection, integration verification and qualified engineering assessment.

Cover every applicable requirement and constraint as far as reasonably and technically feasible, independently of checks elsewhere. Refer ambiguity to the owner of the rule. The coverage record identifies outstanding gaps. It currently lists zero independently derived executable product evaluations. [`02.1-acceptance/deliverables/coverage.md`](deliverables/coverage.md)
