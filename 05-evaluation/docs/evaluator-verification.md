# Evaluator verification map

Follow an E identifier to its single normative definition and read across for the checks that exercise it. A compound obligation can have a definition-local check, an engine check and an integrated check. The table also identifies obligations that need an authenticated run, the separate sandbox probe or human assessment. Offline checks leave authenticated agent behavior and human verdicts unverified. The functional-check sandbox probe supplies environment-specific evidence for a separate execution boundary. Each run supports only the conditions observed and assessed. For the three verification suites, mixed test modules and fixture qualification, see [Offline verification by responsibility](#offline-verification-by-responsibility). For the independent checks of the selected source, injected bytes and retained evidence, see [Candidate binding and identity](#candidate-binding-and-identity).

## Offline verification by responsibility

The engine tests exercise workspace preparation with supplied bytes, process and capture behavior, and the reusable functional-check interfaces. The standalone smoke uses a synthetic contract and a test-authored edit. The registered smoke goes through integrated Candidate selection, including E5 fixture handling. To check isolation, run the engine discovery root and standalone smoke with only the engine package available. The local Conformance discovery root needs only the engine and Conformance packages. Exclude the source checkout from the import path for each isolation check. [`engine/README.md`](../../engine/README.md) · [`05-evaluation/docs/running-and-reviewing.md` § Run offline checks](running-and-reviewing.md#run-offline-checks)

Definition-local tests qualify fixtures and grade controlled observations. For E33 and E34, the local follow-through tests establish the fixture and project-test behavior. Engine tests exercise reusable check ordering and evidence retention. Integrated tests exercise case selection, check timing, error handling and reports. To establish which validation the evaluated agent performed, inspect that agent's command events and assess its account with the retained rubric. [`03.1-conformance/deliverables/conformance/tests/test_followthrough.py`](../../03.1-conformance/deliverables/conformance/tests/test_followthrough.py) · [`05-evaluation/docs/running-and-reviewing.md` § Investigate a failure or incomplete result](running-and-reviewing.md#investigate-a-failure-or-incomplete-result)

Some verification still spans owners. The requester-guidance, independent-execution and assumption-disclosure grading tests share dependencies with their CLI tests and provisionally stay in Evaluation (E25, E32 and E35 above). Other case-aware runtime and scenario tests also exercise integration. The fake executable and CLI harness belong with that integration. The bounded-inquiry suites share test values through a helper so each suite can be discovered once. For any proposed repartition, review each mixed purpose and retain an executable route for it before accepting a permanent owner. ## Candidate binding and identity

- **Source selection and evidence.** The CLI harness locates the expected staged contract independently of the production selector. The fake-CLI smoke checks the selected path and retained bytes. The all-cases test reads the expected bytes and computes the expected digest independently, then compares both with each case's evidence. These checks distinguish selection of the wrong source, corruption of the saved contract and an incorrect reported digest. [`05-evaluation/deliverables/evaluation/tests/support/cli_harness.py`](../deliverables/evaluation/tests/support/cli_harness.py) · [`05-evaluation/deliverables/evaluation/tests/runtime/test_codex.py`](../deliverables/evaluation/tests/runtime/test_codex.py) · [`05-evaluation/deliverables/evaluation/tests/runtime/test_cli.py`](../deliverables/evaluation/tests/runtime/test_cli.py)
- **Binding within one invocation.** Three tests exercise the CLI boundary. Help, invalid case selection and authentication actions work without reading the Candidate. Changing the selected source after setup leaves the first successfully read bytes in use for every case and for independent durable-finding grading. An unreadable Candidate produces a task failure before agent launch and preserves the required review state. [`05-evaluation/deliverables/evaluation/tests/runtime/test_candidate_binding.py`](../deliverables/evaluation/tests/runtime/test_candidate_binding.py)
- **Trusted initial state.** The durable-finding grader compares the initial observation with the supplied trusted contract. The matching-corrupt-snapshots regression checks that identical wrong bytes in both snapshots produce an infrastructure error. A later edit after correct injection fails the preservation assertion. [`03.1-conformance/deliverables/conformance/tests/test_findings.py`](../../03.1-conformance/deliverables/conformance/tests/test_findings.py)
