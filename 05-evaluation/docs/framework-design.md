# Evaluation framework design

The framework gives each case a disposable workspace, keeps observations available after cleanup, and reports whether each applicable check could reach a verdict. The CLI selects a scenario. Shared Python code runs Codex and captures what happened. Pydantic Evals runs the scenario's evaluators over the captured result. A person assesses criteria that depend on meaning or conduct. For one complete path through these components, follow the [scope-discipline walkthrough](#walkthrough-scope-discipline). For optional stages and failure paths, follow the [runtime lifecycle](#responsibilities-and-dependency-direction).

The requirements in [`05-evaluation/README.md` § Evaluator requirements](../README.md#evaluator-requirements) govern the machinery. The case specifications ([`05-evaluation/README.md` § Case specifications](../README.md#case-specifications)) explain the intended assessment, and scenario modules own the executable policy and exact rubrics. The [`05-evaluation/docs/evaluation-model.md`](evaluation-model.md) bounds the conclusions a review can draw. Use operations ([`05-evaluation/docs/running-and-reviewing.md`](running-and-reviewing.md)) to run and review a case or maintenance ([`05-evaluation/docs/maintaining-evaluations.md`](maintaining-evaluations.md)) to change one.

## Execution and security boundaries

The [engine design](../../engine/docs/framework-design.md) specifies agent execution, observations, deadlines, cleanup and the functional sandbox.

- **Offline configuration and orchestration.** [`05-evaluation/deliverables/evaluation/tests/runtime/test_codex.py`](../deliverables/evaluation/tests/runtime/test_codex.py) checks arguments received by a fake CLI. The [engine command tests](../../engine/tests/runtime/test_codex.py) check profile selection, override keys and values, and execution controls. The offline suite ([`05-evaluation/docs/running-and-reviewing.md` § Run offline checks](running-and-reviewing.md#run-offline-checks)) checks execution orchestration with substitutes. These tests do not run real Codex or establish runtime sandbox enforcement.

All behavioral cases capture initial workspace state before execution and final state after agent process-group cleanup, before temporary-directory removal. Snapshots stay in evaluator-owned memory outside the writable workspace. Filesystem-state assertions use captured observations rather than reopening agent-controlled paths or inferring state from a text summary. The durable-finding-review setup validation ([`03.1-conformance/deliverables/cases/durable-finding-review.md` § Automated assessment](../../03.1-conformance/deliverables/cases/durable-finding-review.md#automated-assessment)) additionally uses the trusted contract bytes supplied for this invocation as evaluator-owned reference data.

Human-review cases enable separate final-response capture. Smoke and scope-discipline retain the raw event log without that capture. The engine specifies byte handling and capture failure behavior. [`engine/docs/framework-design.md` § Observation and capture boundaries](../../engine/docs/framework-design.md#observation-and-capture-boundaries)

The rubric also stays outside the writable fixture, so it does not coach the agent. See [`05-evaluation/docs/running-and-reviewing.md` § Retained evidence](running-and-reviewing.md#retained-evidence) for the manifests and exact-byte copies, and [`engine/requirements/evidence-and-capture.md` § E24](../../engine/requirements/evidence-and-capture.md#e24) for their independent retention.

The per-case `--timeout` defaults to 180 seconds and must be positive and finite. Cleanup precedes the next case, and interruption stops the sequence.

Independent-execution and contract-change-followthrough supply their ordered checks, required files and timeouts. The suite invokes them after agent cleanup and before fixture removal. The other cases grade observations without a functional-check subprocess. E33 governs integrated invocation and error classification. E34 governs retained check evidence. The engine owns sandbox execution. [`05-evaluation/deliverables/requirements/suite-execution-and-results.md` § E33](../deliverables/requirements/suite-execution-and-results.md#e33) · [`05-evaluation/deliverables/requirements/evidence-and-capture.md` § E34](../deliverables/requirements/evidence-and-capture.md#e34) · [`engine/docs/framework-design.md` § Functional-check execution](../../engine/docs/framework-design.md#functional-check-execution)

## Framework architecture

### Directory layout and ownership

Paths below are relative to the repository root. The ordered suite and reports belong to Evaluation. The engine exposes reusable execution and observation services.

| Path | Owns |
| --- | --- |
| `05-evaluation/deliverables/evaluation/__main__.py` | Ordered registration, case selection, integrated orchestration, reports and exit status. |
| `engine/runtime/` | Shared workspace, execution, observation and functional-check machinery. |
| `03.1-conformance/deliverables/conformance/` | Nine provisional clause-based definitions. The infrastructure smoke definition is in `engine/smoke.py`. |
| `engine/tests/runtime/` and `05-evaluation/deliverables/evaluation/tests/runtime/` | Engine verification and integrated execution-policy verification respectively. |
| `03.1-conformance/deliverables/conformance/tests/` and `05-evaluation/deliverables/evaluation/tests/scenarios/` | Isolated grading and fixture checks, and case-aware integration checks respectively. |
| `05-evaluation/deliverables/evaluation/tests/support/` | Fake Codex executable and integrated CLI harness. |
| `engine/tests/offline_smoke.py`, `engine/tests/probe_functional_sandbox.py` | Standalone demonstration and opt-in sandbox check. |

A component becomes a directory only when several independently meaningful files justify that boundary, for example if a scenario's evaluators and fixture grew large enough to be reviewed and changed separately. Keep each scenario definition together. Test ownership follows the boundary exercised. Production and test layouts correspond by responsibility, not file for file.

### Pydantic Evals concepts used here

The framework uses a small part of Pydantic Evals; the [technical references](#technical-references) link its documentation.

- **`Case`**: one named input, here the prompt, with an optional `expected_output`. Each scenario defines one case.
- **`Dataset`**: the cases and the evaluators that grade them. Scenarios expose a factory, such as `scope_dataset()`, so every run builds a fresh dataset.
- **Task**: the function Pydantic calls for each case. [`engine/runtime/evaluation.py`](../../engine/runtime/evaluation.py)'s `evaluate()` builds it around the execution callable: it prepares the workspace, calls the callable, and returns its `ExecutionResult` as the case's output, raising `ExecutionError` when execution failed.
- **`Evaluator` and `EvaluatorContext`**: an evaluator's `evaluate(ctx)` reads `ctx.output` (the `ExecutionResult`) and `ctx.expected_output`, then returns a Boolean or an `EvaluationReason` holding a value and a reason. Each evaluator class yields one named assertion. An exception raised inside an evaluator is an evaluator error, not a false assertion.
- **`EvaluationReport`**: graded cases with their assertions, task failures, and evaluator failures. `write_report()` derives the outcome and exit code from it.

Pydantic Evals runs the task and the evaluators. It does not launch Codex, inspect workspaces, or retain evidence; the runtime modules do.

### Evaluating an agent versus testing the evaluator

The two activities share code but answer different questions:

- **Evaluating an agent:** `python -m evaluation` runs the real Codex CLI on a scenario's fixture, consumes subscription allowance, and produces evidence about that run. [`05-evaluation/docs/evaluation-model.md` § Purpose and evaluation model](evaluation-model.md#purpose-and-evaluation-model) bounds what that evidence establishes.
- **Testing the evaluator:** the offline suite never runs a model. Grading tests call `evaluate()` with test-authored execution functions that edit the fixture as a hypothetical agent would. CLI tests run the real command against `05-evaluation/deliverables/evaluation/tests/support/fake_codex.py`. Passing tests show that grading, evidence, and failure handling behave as specified, not that any agent complies with the contract.
- **Checking the functional-check sandbox:** the opt-in probe exercises that sandbox's filesystem and network restrictions using the installed Codex CLI. It does not verify the evaluated-agent permission profile; see [agent execution](../../engine/docs/framework-design.md#agent-execution) for the separate verification scopes.

### Responsibilities and dependency direction

The CLI composes a selected scenario with shared execution and evaluation mechanisms. Shared infrastructure has no dependency on individual scenarios. Scenario modules use the common interfaces while retaining their prompts, fixtures, assessment policy, and scenario-specific interpretation.

| Responsibility | Owner and boundary |
| --- | --- |
| Case composition and reporting | [`05-evaluation/deliverables/evaluation/__main__.py`](../deliverables/evaluation/__main__.py): one ordered `registered_cases(read_contract)` collection selects lazy dataset factories, fixtures, observation, rubrics, and optional functional checks. Rubric presence determines response capture and pending-review reporting. |
| Evaluation orchestration and results | [`engine/runtime/evaluation.py`](../../engine/runtime/evaluation.py): runs an injected execution callable in fresh workspaces and hands results to Pydantic Evals. Owns shared result/error semantics, observation-completeness validation, and response-presence assessment, without scenario policy. |
| Workspace lifecycle and observations | [`engine/runtime/workspace.py`](../../engine/runtime/workspace.py): prepares and removes fixtures, injects the root contract, safely reads regular files, and captures/compares state. Scenarios supply the meaning of permitted content changes. |
| Controlled agent execution and evidence | [`engine/runtime/codex.py`](../../engine/runtime/codex.py): launches Codex, captures observations, and retains evidence. [`engine/runtime/auth.py`](../../engine/runtime/auth.py) owns profile/authentication operations; [`engine/runtime/process.py`](../../engine/runtime/process.py) owns subprocess lifetimes and cancellation. |
| Individual functional-check execution | [`engine/runtime/functional.py`](../../engine/runtime/functional.py) starts one evaluator-owned check with a disposable unauthenticated profile. The adapter ([`engine/runtime/_check_process.py`](../../engine/runtime/_check_process.py)) enforces the inner check timeout. The shared process runner handles the outer deadline, cancellation and process-group cleanup. Check output bytes and launcher diagnostics return separately. |
| Functional-check orchestration and interpretation | [`engine/runtime/functional_checks.py`](../../engine/runtime/functional_checks.py): validates required observations, selects and runs eligible checks sequentially, retains evidence, accumulates infrastructure errors, and interprets generic results as assertion values and reasons. Reuses `ExecutionResult`, workspace observations, the individual check runner, and `codex.save_json`; imports no scenario. |
| Scenario behavior | The scenario modules ([`03.1-conformance/deliverables/conformance/`](../../03.1-conformance/deliverables/conformance)) own their datasets, exact prompts/fixtures, ordered check scripts, required-file definitions, check timeouts, acceptance criteria, additional assertions, and rubrics. Common mechanisms are reused where their semantics match; scenario-specific policy stays local. |

One evaluation passes through these owners in the following order. Optional stages apply only when the selected case configures them; `smoke`, for example, has no workspace observation, functional checks, response capture, or human review.

1. **Selection and composition.** `main()` validates the arguments and selects entries from `registered_cases(read_contract)`. Each `CaseConfig` supplies a lazy dataset factory, fixture files, a workspace-observation setting, an optional human-review rubric, and an optional post-agent `check_execution` step. A rubric's presence also enables final-response capture and pending-review reporting. The scenario module behind the entry owns the behavioral policy: its prompt, fixture, evaluators, check scripts, and rubric. The stages below are shared mechanisms.
2. **Invocation.** `run_case()` creates the case's evidence directory, writes `review.md` when a rubric exists, and defines the execution callback: a function that accepts a prompt and a workspace path and returns an `ExecutionResult`. That result carries the execution status and error, plus any captured observations, final response, and functional-check results that grading later reads. `run_case()` passes the callback, a freshly built Pydantic `Dataset` (its `Case` holds the prompt; the dataset holds the evaluators), and the fixture mapping to `evaluate()`. `evaluate()` wraps the callback in a task and has Pydantic Evals run that task for one case at a time.
3. **Workspace preparation and agent execution.** Inside the task, `prepare_workspace()` creates the temporary directory, writes the unchanged root contract and then the fixture files, and yields the path to the callback. The callback calls `run_codex()`, which takes the initial snapshot when observation is enabled, saves the contract, prompt, and any initial `message.txt` as evidence, checks prerequisites, and launches Codex through `run_process()`, streaming raw events and diagnostics to the evidence directory. Whether the agent finishes, fails, times out, or is interrupted, `run_process()` stops its process group before returning or raising. `run_codex()` then captures the final response when requested, takes the final snapshot when observing, and writes the execution and workspace evidence. Three things remain distinct: the live workspace, which is disposable; the observations held in the returned `ExecutionResult`; and the evidence files written outside the workspace.
4. **Optional functional checks.** Only cases with a `check_execution` step, currently independent-execution and contract-change-followthrough, continue here. The callback invokes that step after `run_codex()` returns, so agent cleanup has finished while the workspace still exists. In independent-execution, for example, the scenario binds its check sources, required files, and timeout to `functional_checks.run_checks`. That function validates the required files from the captured final observation, runs eligible checks sequentially, records skipped checks with reasons, and retains `checks/` and `functional-checks.json` before returning the result with the check results attached. After an agent execution error, it runs no checks and records that reason. The scenario modules and [functional-check execution](../../engine/docs/framework-design.md#functional-check-execution) own the scripts, isolation, and meaning of the results.
5. **Workspace disposal and grading.** If the returned result has error status, the task raises an execution error inside the workspace context: the workspace is removed and the case is not graded (see [`05-evaluation/docs/running-and-reviewing.md` § Outcomes and exit codes](running-and-reviewing.md#outcomes-and-exit-codes)). Otherwise the task returns the result, and leaving the context removes the workspace. Pydantic Evals then applies the dataset's evaluators to that returned result. Grading uses the captured data in memory—workspace observations, functional-check results, the final response, `file_contents`, and the status and error—alongside evaluator-owned reference data such as durable-finding-review's initial-contract validation ([`03.1-conformance/deliverables/cases/durable-finding-review.md` § Automated assessment](../../03.1-conformance/deliverables/cases/durable-finding-review.md#automated-assessment)); it does not reopen the disposed workspace. Separately, the evidence files written in stages 2–4 remain on disk for later inspection.
6. **Reports and human review.** `evaluate()` returns Pydantic's report. `write_report()` derives the outcome and exit code, prints the result, and attempts `report.txt` and `report.json` independently. Completed execution does not imply passing assertions, and automated assertions cover only their defined technical conditions. A human-review rubric remains outside automated grading; its pending flag never overrides error or assertion-failure precedence. [`05-evaluation/docs/running-and-reviewing.md` § Outcomes and exit codes](running-and-reviewing.md#outcomes-and-exit-codes) explains the classification, and [`05-evaluation/docs/running-and-reviewing.md` § Retained evidence](running-and-reviewing.md#retained-evidence) lists the files.

**Cancellation and threading.** Pydantic runs the synchronous task in a worker thread, but Python runs signal handlers only on the main thread, where raising `KeyboardInterrupt` would not stop the worker. `main()` therefore wraps the case sequence in `cancellation_signals()` from [`engine/runtime/process.py`](../../engine/runtime/process.py), whose SIGINT and SIGTERM handlers only set a shared cancellation event and are restored afterward. `run_case()` passes that event to `run_codex()` and the functional-check step. Each launcher (`codex.py` and `auth.py` for Codex and its prerequisite checks, `functional.py` for each check) runs its subprocess through `run_process()`, which observes the event while waiting and stops that process group. Other operations, such as snapshots, evidence writes, and grading, are not interrupted midway. An interruption noticed after evaluation, including during reporting, still makes the case an execution failure, and no further case starts. [Deadlines and cleanup](../../engine/docs/framework-design.md#deadlines-and-cleanup) gives the polling interval, termination sequence, and cleanup limits.

Pydantic owns assertion results/reasons and terminal formatting; the custom code supplies observations and assessment policy. Standard-library filesystem facilities preserve the required byte, permission, and link semantics.

### Walkthrough: scope-discipline

This case shows each owner in a run without optional stages: no functional checks, response capture, or human review.

1. **Definition.** [`03.1-conformance/deliverables/conformance/scope.py`](../../03.1-conformance/deliverables/conformance/scope.py) holds `PROMPT`, which asks for the greeting in `message.txt` to change, and `INITIAL_CONTENTS`, the fixture's exact bytes. `scope_dataset()` returns a `Dataset` with one `Case`, `edit-greeting-only`, whose `expected_output` is the single permitted edit, and two evaluators. `RequestedChange` compares the first line of the captured final `message.txt` with that expectation. `ScopePreserved` calls `scope_violations()`, which delegates to the shared `workspace_violations()` and supplies the one permitted content change. Both call `require_observation()` first, so missing snapshots become evaluator errors rather than verdicts.
2. **Registration.** [`05-evaluation/deliverables/evaluation/__main__.py`](../deliverables/evaluation/__main__.py) registers `CaseConfig("scope-discipline", scope.scope_dataset, {"message.txt": scope.INITIAL_CONTENTS})`. Workspace observation is on by default; with no rubric there is no response capture or pending review, and with no `check_execution` there are no functional checks.
3. **Run.** `python -m evaluation --case scope-discipline --model ID --reasoning-effort VALUE` follows the [lifecycle above](#responsibilities-and-dependency-direction). `prepare_workspace()` writes `AGENTS.md` and `message.txt`; `run_codex()` snapshots the workspace, runs Codex, and snapshots it again; the task returns an `ExecutionResult` holding both snapshots; the workspace is removed; Pydantic applies the two evaluators; `write_report()` prints the outcome.
4. **Result.** `report.json` records `RequestedChange` and `ScopePreserved` with separate reasons. The evidence directory keeps both workspace manifests and `workspace-changes.txt`. The command exits 0 if both pass, 1 if either fails, and 2 on an infrastructure error.
5. **Verification.** [`05-evaluation/deliverables/evaluation/tests/scenarios/test_scope.py`](../deliverables/evaluation/tests/scenarios/test_scope.py) holds its integrated offline tests. `ScopeEvaluationTests` grade test-authored edits through `evaluate()`. `ScopeWorkspaceComparisonTests` in the Conformance tests exercise `scope_violations()` directly. `ScopeCLITests` run the command against the fake executable, whose `scope-discipline` responses are in [`05-evaluation/deliverables/evaluation/tests/support/fake_codex.py`](../deliverables/evaluation/tests/support/fake_codex.py). Run them with `python -m unittest evaluation.tests.scenarios.test_scope conformance.tests.test_scope -v`. The shared behavior they rely on, such as snapshots, evidence, and exit-code precedence, is tested in the engine and Evaluation runtime tests.

Scope-discipline grades only captured observations. Independent-execution and contract-change-followthrough also run evaluator-owned checks on the edited fixture through their `check_execution` entries; their evaluators turn the attached results into assertions with `functional_checks.check_assertion`. [Functional-check execution](../../engine/docs/framework-design.md#functional-check-execution) explains that path.

Internal module locations and imports are implementation details unless a documented contract or demonstrated external consumer requires compatibility. Preserve the documented CLI, execution callable/result semantics, and smoke convenience when changing internal ownership; do not add aliases solely to retain accidental internal interfaces.

### Contract injection and fixture inputs

The CLI selects `04-candidate/pre_AGENTS.md` relative to the stage. The first successful read inside Pydantic task setup binds its exact bytes for the invocation, including every case selected by `all`. An unreadable source produces a task failure. The durable-finding grader independently compares setup observations with the supplied bytes. The launcher hashes and saves the contract actually present in the workspace. A later invocation selects the source again.

The case registration supplies the fixture mapping. The engine owns path validation, workspace preparation and the smoke helper's defaults. [`engine/docs/framework-design.md` § Contract injection and fixture inputs](../../engine/docs/framework-design.md#contract-injection-and-fixture-inputs)

### Evaluation framework package and verification hierarchy

The requester accepted a hierarchy that separates scenario policy, execution machinery and test substitutes. The seven-stage architecture supersedes the earlier package placement, direct contract lookup and one-test-module-per-scenario convention. [`docs/decisions.md` § Seven-stage pipeline and shared evaluation engine](../../docs/decisions.md#seven-stage-pipeline-and-shared-evaluation-engine)

The CLI composes cases. Shared runtime machinery imports no scenario. Each scenario owns its prompt, fixture, assessment policy, and any functional checks or rubric. Reuse between scenarios is explicit, as when independent-execution uses the requester-guidance fixture. The former layout gave each scenario one module and a corresponding offline test module. It grouped cross-scenario CLI checks with shared runtime tests. The [current layout](#directory-layout-and-ownership) assigns verification by the responsibility exercised. Test substitutes have their own owner outside production code.

Flat production and test trees obscure those responsibilities. Organizing just one tree leaves the other ambiguous, and naming only the test side `infrastructure/` obscures its relationship to runtime. A directory for a single-file scenario adds a level without a second responsibility. Test modules importing one another caused discovery to load some modules under two names even though each test ran once. Absolute package-qualified imports and discovery from the respective package roots ([`05-evaluation/docs/running-and-reviewing.md` § Run offline checks](running-and-reviewing.md#run-offline-checks)) avoid duplicate loading. The integrated CLI harness supplies the scenario CLI tests with their fake executable.

Package-qualified imports, mock targets, and subprocess working directories must resolve the same package. The hierarchy deliberately omits compatibility aliases and re-exports because they would hide stale imports. Keep the documented CLI, callable and result contracts, smoke convenience, and standalone offline-smoke and sandbox-probe entry points. `_check_process.py` must stay beside `functional.py`, which locates it by position. The former runtime package resolved the staged source ([`docs/architecture.md` § Staged sources and release-relative references](../../docs/architecture.md#staged-sources-and-release-relative-references)) directly. Evaluation now supplies the contract through the [invocation-scoped reader](#contract-injection-and-fixture-inputs).

Adding a scenario affects its module, registration, tests, fake responses, and cross-scenario case lists. Changes to code ownership preserve E1–E40 and grading semantics. [Offline tests](#evaluating-an-agent-versus-testing-the-evaluator) verify the machinery. Behavioral evidence requires a live run.

### Evaluation documentation by maintenance responsibility

The requester authorized separate documentation for operators, case maintainers and framework maintainers. A single guide kept the lifecycle close to the criteria and evidence, but made readers work through material owned by other responsibilities. The decision concerns documentation ownership. [`docs/decisions.md` § Integrated engineering architecture with focused detailed owners](../../docs/decisions.md#integrated-engineering-architecture-with-focused-detailed-owners)

Case specifications explain assessment and interpretation. Scenario modules own exact inputs, grading and rubric text. Evaluation links to those sources and the engine from the integrated lifecycle, requirements and verification routes. Each historical run retains the interpretation supported by its captured contract, fixture, rubric and evidence.
