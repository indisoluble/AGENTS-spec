# Maintaining evaluations

Paths beginning with `deliverables/` are relative to `05-evaluations/`. For both scenario and shared evaluator changes, use ordinary functions and existing typed result records for composition, `Path` for filesystem boundaries, and bytes where exact fixture or evidence preservation matters.

When applied in a consuming project, the candidate contract's [engineering rules](../../04-candidate/pre_AGENTS.md#12-do--perform-the-authorized-work) and [validation rules](../../04-candidate/pre_AGENTS.md#13-study--assess-completion-and-learning) cover production modules, tests, fixtures, and testing utilities alike. In this repository the staged candidate serves only as source material.

## Establish the expectation

What would a pass tell the reader? Start with the source that can justify that conclusion.

| Purpose | Where the expectation comes from | How to make it observable |
| --- | --- | --- |
| Verify evaluator functionality | The applicable [E requirement](../README.md#evaluator-requirements), including its conditions and error paths | Supply a known observation or a controlled failure. Check what the evaluator returns and retains. [Smoke](../deliverables/cases/smoke.md) exercises the execution and grading path. Its offline substitute supplies the edit itself. |
| Exercise a selected contract clause | The clause in the identified Candidate and its mechanism in the [shared clause index](../../docs/contract-traces.md#contract-clause-index) | Put the agent in a situation that triggers the clause. Preserve the actual duty, permission, recommendation or exception. Use the [case specification](../README.md#case-specifications) to explain which conduct can be judged from the resulting evidence. |
| Assess an accepted product outcome | The accepted rule and version in Formulation, its conditions, and any example expressly accepted as defining | Before the check guides authorized implementation, describe what an agent could do to satisfy the rule and what would violate it under the same conditions. Allow the outcomes the rule permits, including outcomes achievable by a different design. [Requirements handoff](../../docs/changing-the-contract.md#apply-an-authorized-behavior-change) · [Test-first iteration](../../docs/pipeline.md#test-first-iteration) |

For example, BR3 requires prior direction for a new consequential architectural choice unless the specific choice already has authorization. To assess an agent that adopted such a choice, a reviewer would need to establish what the requester had authorized and whether the agent obtained any necessary direction before adoption. A final disclosure alone cannot establish prior direction. This distinction comes from the accepted rule. The current timezone case exercises unresolved intent under the selected clause. [BR3](../../02-formulation/deliverables/baseline.md#br3--autonomy-within-authorization-and-prior-direction) · [Requester-guidance](../deliverables/cases/requester-guidance.md#situation-and-objective)

If the proposed expectation turns on an unsettled product distinction, take it to [Discovery](../../01-discovery/deliverables/open-questions.md). For a defining example, look in Formulation for the decision in which the requester or an explicitly authorized delegate accepted that version and its conditions. A Discovery label, a BDD-style example, or a passing case supplies no such decision. All current Discovery examples remain proposed. [How to recognize a defining example](../../02-formulation/docs/maintaining-formulation.md#determine-whether-an-example-defines-the-rule) · [Decision authority](../../docs/authority.md#development-decisions)

Choose fixture facts and a task that expose the distinction. Identify which observations would let an assertion or reviewer distinguish the allowed and violating responses, and what would remain unknown if an observation were missing. For a claim about communication or timing, initial and final files alone can be identical in both cases. Check that the events, response and any other evidence needed for review will survive workspace cleanup. Keep the purpose, governing source and interpretation in the case specification. The module owns the exact prompt, fixture, assertions and rubric.

## Change a scenario

Start with the [case specification](../README.md#case-specifications) for the intended behavior, assessment criteria, and links to the scenario module and tests. A scenario change should normally involve those local owners, one `CASES` entry where configuration changes, and affected documentation.

The scenario module owns the task, fixture, dataset, evaluators, and optional human rubric. Reuse shared execution, workspace observation, response capture, and evidence mechanisms. In the CLI entry, register a lazy dataset factory. Select the existing observation and review settings and, only where needed, the post-execution functional check. Keep that check after agent cleanup and before fixture removal.

Trace the changed fact to its direct users. For example, [independence.py](../deliverables/scenarios/independence.py) reuses exporter fixture data from [guidance.py](../deliverables/scenarios/guidance.py). For clause edits, inspect numbered rubric references in [assumptions.py](../deliverables/scenarios/assumptions.py), [inquiry.py](../deliverables/scenarios/inquiry.py), and [findings.py](../deliverables/scenarios/findings.py), as well as unnumbered criteria and implicit assertions such as `ScopePreserved` in [scope.py](../deliverables/scenarios/scope.py). No automated check detects a stale clause reference or a change in its meaning.

For [bounded-inquiry](../deliverables/cases/bounded-inquiry.md#human-review), the prompt already communicates the main uncertainty. If §2.4 changes, check what the fixture actually triggers and how the scenario rubric treats a second notice. A renumbering can need only a reference repair. Changing the expected verdict under the same conditions needs direction from the requester or someone explicitly authorized to decide it. For a requirements-led case, revisit the accepted rule and conditions even if the new clause suggests a different verdict. Earlier assessments stay tied to their original criteria. ## Add a scenario

Start with the [expectation and evidence](#establish-the-expectation). Adding a registered case requires authorization to revise the accepted selections in [E12](../deliverables/requirements/suite-execution-and-results.md#e12) and the order in [E15](../deliverables/requirements/suite-execution-and-results.md#e15). Check the other affected requirements, including [E26](../deliverables/requirements/suite-execution-and-results.md#e26) for a case needing human review. Explain the intended assessment, limits and applicable case-specific evaluator requirements in `deliverables/cases/<case-name>.md`.

1. Create `deliverables/scenarios/<module>.py` with `PROMPT`, the fixture bytes, its evaluators, and a dataset factory returning a one-case `Dataset`. Add `REVIEW_RUBRIC` if a person must judge meaning or conduct. Add a `check_execution` wrapper over `functional_checks.run_checks` if grading needs to run evaluator-owned scripts on the edited fixture. Import shared mechanisms from `deliverables.runtime`.
2. Add a `CaseConfig` entry to `CASES` in [deliverables/__main__.py](../deliverables/__main__.py) at the position defined by [E15](../deliverables/requirements/suite-execution-and-results.md#e15). The `--case` choices and the `all` order come from that collection.
3. Teach [fake_codex.py](../deliverables/tests/support/fake_codex.py) to recognize the case from its prompt or fixture and to produce the scripted responses its tests need.
4. Add `deliverables/tests/scenarios/test_<module>.py` with grading tests through `evaluate()` and a `<Name>CLITests(FakeCodexCLI, unittest.TestCase)` class for CLI composition, evidence, and failure classification.
5. In [test_cli.py](../deliverables/tests/runtime/test_cli.py), update the tests that enumerate every case. They cover all-cases order and evidence, late-case precedence, and aggregate exit codes.
6. Link the case specification to its module, tests and applicable shared requirements. Link it from the [stage README](../README.md#case-specifications).
7. [Verify the change](#verify-a-behavior-change), including the offline checks.

## Change shared evaluator functionality

Locate the affected component in [framework responsibilities](framework-design.md#responsibilities-and-dependency-direction) and its applicable [shared requirements and their Checks](../README.md#evaluator-requirements). Keep common mechanisms with the component responsible for them. Two callers alone do not justify a generic utility. Keep case-specific grading policy in the scenario module.

Preserve the [interfaces used by scenarios and substitutes](framework-design.md#interfaces-used-by-scenarios-and-substitutes). Supply execution dependencies at the existing callable boundary for offline tests. Keep missing observations distinct from empty state and infrastructure errors distinct from false assertions.

For example, a correction to snapshot comparison starts in [workspace.py](../deliverables/runtime/workspace.py). Read the [snapshot and inspection requirements](../deliverables/requirements/workspace-and-observation.md#e16), then find callers of the affected function. For `workspace_violations`, check the permitted greeting edit in [scope.py](../deliverables/scenarios/scope.py) against [E18](../deliverables/cases/scope-discipline.md#e18), along with the other callers' own content rules. Use [test_workspace.py](../deliverables/tests/runtime/test_workspace.py) for comparison and missing-byte errors, then the affected scenario tests for the attribution of each assertion. A shared correction under the existing requirement preserves those verdicts.

## Verify a behavior change

Use the existing substitutes and fake CLI to verify outcomes, independent assertions, error classification, evidence, and resource cleanup at the affected boundary. Preserve meaningful negative cases. Derive expected results independently of production grading and configuration logic. Keep scenario-specific test expectations local, sharing setup only when it clarifies the tests.

When behavior changes, update the assessment and interpretation in the affected [case specification](../README.md#case-specifications). Update [E1–E40](../README.md#evaluator-requirements) only through an authorized requirement change. Source remains canonical for exact fixture bytes, prompts, check scripts, and rubric text. Check direct documentation links.

Run the [offline checks](running-and-reviewing.md#run-offline-checks). The [case specifications](../README.md#case-specifications) and [evaluator requirements](../README.md#evaluator-requirements) link the relevant regression tests. The [shared tests](../deliverables/tests/runtime) cover authentication, cancellation, filesystem observation, and evidence failures. For a revised human rubric, compare the criteria with their governing source, including the applicable contract provisions for a clause-based case. Preserve rule strengths, triggers, exceptions, evidence limits and unaffected technical checks. Offline tests verify infrastructure and technical assertions. They cannot establish rubric semantic validity or live contractual compliance. See the [evaluation model](evaluation-model.md#purpose-and-evaluation-model) for the limits of behavioral evidence.

Live verification requires inspecting one [separately authorized run](running-and-reviewing.md#run-a-case-or-the-suite). If authorization covers only offline work, stop after that verification and report live assessment as pending. The [functional-check sandbox probe](framework-design.md#functional-check-execution) checks that separate boundary's runtime enforcement. Verification of the evaluated-agent permission profile and authenticated integration follows the distinct scopes in [agent execution](framework-design.md#agent-execution).

Inspect the [retained evidence](running-and-reviewing.md#retained-evidence) for the live run's selected case, assertions and reasons, initial/final bytes and available manifests, contract hash, model settings, and cleaned workspace path. For human-review cases, also inspect response capture, readable differences, the retained rubric, and pending-review reporting, and follow the [human review procedure](running-and-reviewing.md#response-presence-and-human-review) to assess the rubric with the requester. For independent-execution and contract-change-followthrough, include functional-check evidence. Each executed case should produce a distinct workspace and evidence directory. Keep run-specific findings and results with that evidence.

Route a finding according to what the evidence calls into question. A fixture that reveals the answer, an observation failure, or a grading error belongs in Evaluations. A discrepancy between the selected mechanism and its instructions belongs with Design and Candidate. Take unsettled intent to Discovery and the decision owner. Formulation records an authorized change to product intent. If the evidence cannot distinguish these explanations, keep the finding inconclusive.
